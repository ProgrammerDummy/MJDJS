    struct Job {
      id: String,          // will become UUID v7 in the project
      job_type: String,
      payload: Vec<u8>,

      retry_count: u32,

      Queued,
      Running { worker_id: String, started_at: u64 },
      Succeeded { completed_at: u64 },
      Failed { error: String, attempts: u32 },
      Retrying { retry_at: u64, attempts: u32 },
      DeadLettered { reason: String },
    }

  Implement: Display, Debug, Clone on all types.
  Implement: fn transition(current: JobState, event: JobEvent) -> Result<JobState, TransitionError>
  Invalid transitions (e.g. Succeeded → Running) return Err — never panic.

  Valid transitions to implement:
    Queued → Running       (event: Dispatched { worker_id })
    Running → Succeeded    (event: Completed)
    Running → Failed       (event: WorkerError { error })
    Failed → Retrying      (event: RetryScheduled { retry_at })
    Failed → DeadLettered  (event: ExhaustedRetries { reason })

    Running → Queued       (event: WorkerDied — heartbeat timeout)
    Queued → Cancelled     (event: Cancelled)
    Running → Cancelled    (event: Cancelled — via CancellationToken)

── TOKIO CHANNEL TYPES — LEARN ALL 4 ───────────────────────────────────────────

You will use ALL 4 of these in the project. Know each one:

mpsc (multi-producer, single-consumer):
  tokio::sync::mpsc::channel(buffer_size)
  USE FOR: job submissions from clients → scheduler
  USE FOR: scheduler dispatching jobs → each worker task
  Bounded: provides backpressure (sender blocks when full)
  Unbounded: no backpressure (use only when you control the sender rate)

oneshot (single-use, single message):
  tokio::sync::oneshot::channel()
  USE FOR: worker reporting a single job result back to scheduler
  USE FOR: cancel signal from scheduler to a specific running job
  After sending once, channel is consumed.

broadcast (one sender, many receivers):
  tokio::sync::broadcast::channel(capacity)
  USE FOR: scheduler broadcasting shutdown signal to all workers
  Every receiver gets every message. Lagging receivers get errors.

watch (latest value, many readers):
  tokio::sync::watch::channel(initial_value)
  USE FOR: scheduler broadcasting current capacity / health state
  Receivers always get the most recent value (not historical).

[MUST] Build the simulated scheduler — channels only, no networking
  This is the core scheduler logic, proven locally before adding gRPC.
  
  Architecture:
    1. Scheduler task: receives job submissions on mpsc::Receiver<Job>
       Maintains BinaryHeap<QueuedJob> (priority queue from week 1)
       Dispatches jobs to worker tasks via per-worker mpsc::Sender<Job>
       Receives results on mpsc::Receiver<(JobId, JobResult)>
    
    2. Worker tasks (N of them):
       Each has: mpsc::Receiver<Job> (receives from scheduler)
       Shared: mpsc::Sender<(JobId, JobResult)> (sends results to scheduler)
       Processes one job at a time (or max_concurrent_jobs at a time)
    
    3. Shutdown: broadcast::Sender<()> (scheduler sends to all workers)
                 CancellationToken (workers pass to job executors)

  Channel assignments:
    Job submission:  mpsc — client → scheduler
    Job dispatch:    mpsc — scheduler → each worker (one channel per worker)
    Job result:      mpsc — all workers → scheduler (shared sender, cloned)
    Shutdown signal: broadcast — scheduler → all workers
    Capacity state:  watch — scheduler broadcasts current queue depth

  Tests required:
    - Submit 50 jobs with mixed priorities → verify execution is priority-ordered
    - Submit 100 jobs to 5 workers → verify all 100 complete, none lost
    - Submit 200 jobs (more than worker capacity) → verify queuing is correct
