## Project Overview
MJDJS is a general-purpose distributed job scheduler built in Rust, as a resume and
learning project targeting systems/infrastructure SWE roles. The scheduler treats
jobs as opaque units of work — it doesn't care what a job's payload means, only that
jobs get executed, retried on failure, and reported on when done.

**Language:** Rust (2021/2024 edition, mixed across crates — check each Cargo.toml).
**Structure:** a 4-crate Cargo workspace (details below), replacing an earlier
single-crate structure.
**Roadmap:** 4 phases, 16 weeks total. Phase 1 (Weeks 1–4) is complete. Currently
starting Phase 2 (Weeks 5–8).

## Project Structure (current, as of end of Week 4)

4-crate Cargo workspace, root `Cargo.toml` is **virtual** (no `[package]`, only
`[workspace]` + `[workspace.dependencies]`):

- **scheduler-core** (lib) — owns the proto schema and all codegen. Contains
  `job_data_structures.rs` (Job, JobState, RetryPolicy, JobQueue), `state_machine.rs`
  (JobEvent, transition(), determine_next_event(), full test suite),
  `conversion.rs` (ConversionError + bidirectional TryFrom conversions between
  internal types and generated proto types), and `proto/scheduler.proto`. Only this
  crate runs `tonic-prost-build` in its `build.rs` (at the crate root, not in
  `src/`). `lib.rs` exposes `pub mod proto { tonic::include_proto!("scheduler"); }`.
- **scheduler-server** (bin) — the actual gRPC server process. `main.rs` stands up
  `tonic::transport::Server`, binds to an address configurable via the
  `SCHEDULER_ADDR` env var (falls back to a hardcoded default). `service.rs` has
  `MySchedulerService` implementing the generated `SchedulerService` trait.
  `submit_job` and `get_job_status` are fully implemented and tested end-to-end
  over real gRPC. The other five RPCs (`cancel_job`, `requeue_from_dlq`,
  `create_template`, `list_jobs`, `list_dead_lettered`) are honest
  `Status::unimplemented` stubs — deliberately out of Week 4 scope, not gaps.
- **worker-agent** (bin) — not yet built. Will be the gRPC *client* for
  `WorkerService` (workers dial the scheduler, not the other way around).
- **scheduler-client** (lib, likely with a bin CLI target too) — not yet built.
  Typed client wrapper for `SchedulerService`, meant to be reused by a future CLI
  and eventually a web dashboard.

**Important:** the *old* Phase 1 in-process, single-node, simulated scheduler
(`scheduler.rs`, `worker.rs` — `Scheduler<T>`, `WorkerPool<T: Runnable>`, the
`tokio::select!` dispatch loop) was moved out of the workspace entirely into a
`reference/` directory at the repo root. It is **not compiled, not part of any
crate**. It's kept only as a reference for patterns (cancellation-token racing,
graceful shutdown, the `Abandoned` state design) — it will very likely need
substantial redesign, not a literal port, because the whole dispatch model changed
(see "Push vs. pull dispatch" below).

## Key Architectural Decisions Worth Knowing Up Front

(Not exhaustive — see DECISIONS.md for the full record with reasoning. This is the
short list of things that will matter immediately in Week 5.)

- **Server is sole authority for `id`, `state`, and `created_at`** on job admission.
  Client-supplied values for these three are always overwritten, never trusted —
  this prevents ID collisions, guarantees an accurate initial state, and prevents a
  client from gaming the priority-queue tiebreaker by lying about submission time.
- **UUID v7 for job IDs**, wired as `bytes` on the wire — coordination-free
  uniqueness across many clients, plus rough time-ordering that matches the
  existing `created_at` tiebreak and will matter for SQLite insertion locality.
- **`job_type` is a `string` routing key**, not a `u64` — meant to be matched
  against worker capabilities.
- **`requirements`/`capabilities` are matched by dispatch logic; `metadata`/`tags`
  are purely descriptive and the scheduler never reads them.** Same split, mirrored
  on both `Job` and `Worker`.
- **Both proto↔internal `Job` conversions are `TryFrom`, not `From`** — a `Duration`
  conversion can fail in both directions, and a bare `.unwrap()` on it was a real,
  found crash risk from client-supplied values.
- **Dispatch is pull-based (`RequestWork`), not push-based** like the old in-process
  scheduler. This is a deliberate divergence from a literal reading of the
  roadmap's Week 5 text (which is written in push language) — logged explicitly in
  DECISIONS.md. Pull-based dispatch gives inherent load balancing and makes an idle
  worker's death a non-event, for free, structurally — analogous to a Kafka
  consumer group. **It does NOT give free fault tolerance for a worker that dies
  mid-job** — a worker that received a job via `RequestWork` and then crashes
  leaves that job stuck with nothing currently able to reclaim it. This was an
  earlier overclaim that got corrected in the log (entry 21) — worth knowing so it
  doesn't get assumed as already-solved going into Phase 3.
- **`Heartbeat` is bidirectional streaming** specifically so the scheduler can push
  control messages (e.g. "stop accepting new work" on a graceful leader stepdown)
  down an already-open connection — something client-streaming is structurally
  incapable of.
- **Unresolved tension, worth resurfacing early in Week 5:** the roadmap's own
  Week 5 text describes the dispatch loop in push terms ("find available worker...
  dispatch to worker"), which sits awkwardly next to the pull-based `RequestWork`
  design already committed to in the schema. Not reconciled yet — worth addressing
  directly before building `SchedulerState`'s dispatch logic, not after.
- **Known schema smell, deliberately deferred:** `proto::Job` currently serves
  double duty as both "the full representation of an existing job" and "SubmitJob's
  request payload," forcing a client submitting a new job to supply placeholder
  values (id, state) that the server immediately overwrites. The correct fix — a
  dedicated `SubmitJobRequest` message — was deferred rather than done mid-Week-4.
  Worth reconsidering before Phase 2 persistence makes schema changes more
  expensive to make.
- **Recurring gotcha, already hit multiple times:** every singular *message-typed*
  proto field (not scalars) is `Option<T>` in generated Rust, always, no
  exceptions — this has caused real bugs every time it was missed.
- **gRPC status codes are chosen deliberately, not defaulted:** `InvalidArgument`
  for malformed/policy-violating input, `NotFound` for well-formed-but-nonexistent
  lookups, `Internal` for "this should be structurally impossible given our own
  validation — it's our bug, not the caller's."

## Testing Philosophy Established This Project

- A test with an empty body, an empty match arm, or a missing `return` can "pass"
  while proving absolutely nothing — this has happened for real, multiple times,
  and is always caught by actually reading the source, never by trusting a green
  checkmark or a "N passed" count alone.
- Prefer real infrastructure in tests where feasible: the Week 4 integration tests
  bind a real `TcpListener`, spawn a real server, and connect a real gRPC client —
  not mocked.
- Correct pattern for "is the test server ready" in an async test: bind the
  `TcpListener` via `.await` *before* spawning the server task — the bind
  completing IS the readiness guarantee, no separate signal needed. An earlier
  `oneshot`-channel-based readiness signal was a real, found bug (wired to the
  wrong event — server *shutdown* completing, not startup).
