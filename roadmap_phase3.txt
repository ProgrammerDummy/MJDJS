[MUST] Implement leader election using etcd leases
  URL: docs.rs/etcd-client
  
  On scheduler startup:
    1. Grant etcd lease with 10-second TTL:
         let lease = etcd.lease_grant(10, None).await?;
    2. Try to PUT scheduler/leader with own node_id, attached to the lease:
         etcd.put("scheduler/leader", node_id, Some(PutOptions::new().with_lease(lease.id()))).await?;
    3. If PUT succeeds (key didn't exist) → BECOME LEADER:
         - Start renewing lease every 3 seconds (keep_alive loop)
         - Load all incomplete jobs from SQLite → re-queue them
         - Start the dispatch loop
         - Start the heartbeat checker
    4. If PUT fails (key exists, another scheduler is leader) → BECOME STANDBY:
         - Watch the key for changes: etcd.watch("scheduler/leader").await?
         - When key is deleted (lease expired): retry step 2

  On losing leadership (lease renewal failure or explicit yield):
    - Stop dispatch loop
    - Stop accepting new job submissions (return UNAVAILABLE to clients)
    - Stop heartbeat checker
    - Transition to standby mode

  Lease renewal loop (runs while leader):
    Every 3 seconds:
      if etcd.lease_keep_alive(lease_id).await is Err:
        // Connection to etcd lost — we may have lost leadership
        // Do not dispatch any more jobs until we re-confirm leadership
        attempt_to_become_leader()

[MUST] Implement tag-based worker routing
  Workers declare tags on registration:
    tags: map<string, string> = {"gpu": "true", "region": "us-east", "memory_gb": "32"}
  
  Jobs declare requirements on submission:
    requirements: map<string, string> = {"gpu": "true"}
  
  Dispatch rule: job routes to worker ONLY IF job.requirements ⊆ worker.tags
  (every key in job.requirements must exist in worker.tags with the same value)
  
  Implementation in dispatch loop:
    fn worker_matches_job(worker: &WorkerInfo, job: &QueuedJob) -> bool {
      job.requirements.iter().all(|(k, v)| {
        worker.tags.get(k).map(|wv| wv == v).unwrap_or(false)
      })
    }
  
  If no matching worker is available: job stays in queue until a matching worker
  is free. This can cause priority inversion (a low-priority job might be
  dispatchable while a high-priority job waits for a specific worker type).
  Document this as a known limitation.
  
  Tests:
    - 3 GPU workers, 3 CPU workers: 10 GPU jobs + 10 CPU jobs
    - Verify: GPU jobs ONLY run on gpu=true workers (check logs + SQLite worker_id)
    - Verify: CPU jobs can run on any worker
  
  On school servers: label machines with real tags based on actual hardware.

[MUST] Implement resource-aware scheduling
  Workers declare on registration:
    available_cpu_cores: u32
    available_memory_mb: u32
  
  Jobs declare on submission:
    requires_cpu_cores: u32     (default: 1)
    requires_memory_mb: u32     (default: 256)
  
  Scheduler tracks per worker (in WorkerInfo):
    allocated_cpu: AtomicU32
    allocated_memory: AtomicU32
  
  Dispatch rule: worker can receive a job ONLY IF:
    worker.available_cpu - worker.allocated_cpu >= job.requires_cpu_cores
    AND
    worker.available_memory - worker.allocated_memory >= job.requires_memory_mb
  
  On dispatch: increment allocated_cpu and allocated_memory
  On job completion: decrement allocated_cpu and allocated_memory
  
  Tests:

      Verify: max 4 run concurrently, 5th and 6th wait.
    - Worker: 8192 MB RAM. Submit job requiring 10000 MB.

[MUST] Implement priority starvation prevention (aging)
  Problem: A constant stream of high-priority jobs can starve low-priority ones.
  Solution: Aging — boost a job's effective_priority by 1 every N seconds it waits.
  
  Add to QueuedJob:
    effective_priority: u32,    // starts = original priority, boosted by aging
    original_priority: u32,     // immutable — what the user submitted
    queued_at: Instant,         // when the job entered the queue
  
  Background task (runs every 30 seconds):
    for each job in job_queue:
      wait_seconds = now - job.queued_at
      if wait_seconds > aging_threshold_seconds (config, default: 300):
        boosts = (wait_seconds / aging_interval_seconds) as u32
        job.effective_priority = min(
          job.original_priority + boosts,
          10  // cap at max priority
        )
        // Re-insert into BinaryHeap (remove + re-insert since BinaryHeap is immutable)
  
  Note: BinaryHeap does not support in-place mutation. To update a job's priority:
    1. Drain the entire heap into a Vec
    2. Modify the job's effective_priority
    3. Rebuild the heap from the Vec
  This is O(n) — acceptable for a background task running every 30 seconds.
  
  Tests:
    - Submit 1000 high-priority (priority=9) jobs
    - Submit 1 low-priority (priority=1) job
    - Verify: the low-priority job eventually runs despite constant high-priority traffic
    - Log every priority boost: job_id, original_priority, new_effective_priority

[MUST] Implement global token bucket rate limiter
  This limits the TOTAL jobs dispatched per second across all types.
  
  struct TokenBucket {
    capacity: u32,           // max tokens (burst size)
    tokens: AtomicU32,       // current tokens available
    last_refill: AtomicU64,  // Unix ms of last refill
    refill_rate_per_sec: u32, // tokens added per second
  }
  
  impl TokenBucket {
    fn try_consume(&self) -> bool {
      // 1. Compute tokens to add since last_refill:
      //    elapsed_ms = now - last_refill
      //    tokens_to_add = (elapsed_ms * refill_rate_per_sec) / 1000
      // 2. Add tokens (capped at capacity)
      // 3. Update last_refill
      // 4. If tokens > 0: decrement and return true
      // 5. Else: return false (caller waits and retries)
    }
  }
  
  IMPORTANT: Use INTEGER tokens (not float). Float drift causes incorrect behavior
  over long runtimes. Multiply by 1000 for sub-1-per-second rates.
  
  In dispatch loop: before each dispatch, call token_bucket.try_consume().
  If false: sleep until next token (1000ms / refill_rate_per_sec) and retry.
  
  Tests:
    - Set rate limit to 10 jobs/sec, submit 100 jobs to 20 workers
    - Measure throughput every second for 10 seconds
    - Verify: throughput is 10 ± 1 jobs/sec in EVERY window (not just average)
    - A spiky profile means your token refill is batching — fix it

[MUST] Implement fan-out jobs (parent-child, depth=1 ONLY)
  A running job can spawn child jobs via ScheduleChildren RPC.
  Parent job remains Running until ALL children complete.
  If any child fails and exhausts retries: parent is marked Failed.
  
  Data model additions:
    Add parent_id: Option<JobId> to Job struct and SQLite schema
    Add children: Arc<DashMap<JobId, ChildStatus>> to track parent's children
  
  ScheduleChildren RPC (called by a running job):
    1. Validate caller is actually Running (check running_jobs map)
    2. Validate depth: if caller has a parent_id, reject (max depth = 1)
    3. Submit each child job (same as SubmitJob but with parent_id set)
    4. Record children in parent's tracking structure
  
  Completion listener (called whenever a job completes):
    if job.parent_id is Some:
      parent_children = get_children_of(parent_id)
      if all children are Succeeded:
        mark parent as Succeeded
      elif any child is DeadLettered:
        mark parent as Failed { reason: "child job {id} dead-lettered" }
      // else: some children still running, do nothing yet
  
  Circular dependency detection:
    Before accepting a ScheduleChildren call, check: is the caller's job_id
    anywhere in the ancestry of the proposed children? (Build ancestry by
    following parent_id chain. With depth=1, this is just: does any proposed
    child have the same id as an ancestor?)
    If circular: return INVALID_ARGUMENT
  
  Tests:
    - Parent spawns 5 children, all succeed → parent becomes Succeeded
    - Parent spawns 5 children, 2 dead-letter → parent becomes Failed
    - Attempt to spawn grandchildren → rejected with INVALID_ARGUMENT
  
  Document in README: "Fan-out supports depth=1 (parent-child only).
  Full DAG dependencies are not supported."

  last_refill on every try_consume call, add proportional tokens, update last_refill.

[MUST] "Falsehoods Programmers Believe About Time"
  Google: "falsehoods programmers believe about time"
  Read BEFORE touching any cron or timestamp code. Non-negotiable.
  Timezone and DST bugs are the most common cron implementation mistakes.
  Key falsehoods for your cron:

    - "The local time zone can be determined by the server's clock" → don't trust it

  display time. NEVER store local time. This is absolute.

      template_id TEXT NOT NULL,     -- references job_templates table
      last_fired_at INTEGER,         -- Unix ms UTC (NULL if never fired)
      next_fire_at INTEGER NOT NULL, -- Unix ms UTC
      concurrency_policy TEXT NOT NULL DEFAULT 'Forbid',
      enabled INTEGER NOT NULL DEFAULT 1,
      created_at INTEGER NOT NULL
    );
  
  On startup AND after each leader election:
    Load all enabled cron jobs from SQLite.
    For each: compute next_fire_at using:
      let schedule = cron::Schedule::from_str(&expression)?;
      let next = schedule.after(&Utc::now()).next()?;
      next_fire_at = next.timestamp_millis() as u64;
    
  Tests:

    - Expression "0 9 * * 1-5" → next_fire_at skips weekends

[MUST] Implement the cron tick loop
  A dedicated tokio task that wakes at the earliest next_fire_at.
  Uses tokio::time::sleep_until — NOT polling every second.
  
  Loop:
    1. Find earliest next_fire_at across all enabled cron jobs
    2. sleep_until(earliest_next_fire_at)
    3. For each cron job where next_fire_at <= now:
       a. CHECK IDEMPOTENCY GUARD:
            current_interval_start = floor_to_cron_interval(now, expression)
            if last_fired_at >= current_interval_start:
              // Already fired this interval (e.g., after failover)
              skip — do not fire again
       b. Check concurrency policy (Forbid: skip if previous still Running)
       c. Submit a job using the referenced template (call SubmitFromTemplate)
       d. Update last_fired_at = now, compute new next_fire_at
       e. Write both to SQLite (atomically — single transaction)
    4. Go back to step 1
  
  THE IDEMPOTENCY GUARD IS THE CRITICAL PART:
  After a leader failover, the new leader loads cron jobs from SQLite and
  starts the tick loop. If last_fired_at is within the current cron interval,
  it means the old leader already fired it. The guard prevents double-firing.
  Without the guard: every failover causes a duplicate cron job execution.
  
  Tests:
    - Set cron to every 1 minute, crash scheduler at 30s into a minute
    - Restart. Verify: exactly 1 job fires per minute, not 0, not 2.
    - Failover mid-minute (kill leader, standby takes over)
    - Verify: exactly 1 firing for that minute across both leaders.
