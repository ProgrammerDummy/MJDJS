PROTO SCHEMA OVERVIEW
----------------------
Services:
  SchedulerService { SubmitJob, GetJobStatus, CancelJob, ListJobs,
                     CreateTemplate, ListDeadLettered, RequeueFromDLQ }
  WorkerService { Register, Heartbeat (bidirectional stream),
                  ReportResult, RequestWork, ScheduleChildren }

Key fields on Job proto:
  - id: uint64 (UUID v7 — time-ordered)
  - job_type: string (routing key)
  - payload: bytes
  - priority: uint32 (1–10, higher = first)
  - requirements: map<string, string> (tag matching for worker routing)
  - metadata: map<string, string> (user tags)
  - retry_policy: RetryPolicy message

JOB STATE MACHINE
------------------
States: Queued, Running { worker_id, started_at }, Succeeded { completed_at },
        Failed { error, attempts }, Retrying { retry_at, attempts },
        DeadLettered { reason }

Transitions (fn transition(state, event) -> Result<JobState, Error>):
  Queued      → Running       (dispatched to worker)
  Running     → Succeeded     (worker reports success)
  Running     → Failed        (worker reports failure)
  Failed      → Retrying      (retry_count < max_attempts)
  Failed      → DeadLettered  (retry_count >= max_attempts)
  Retrying    → Queued        (retry_at <= now, re-enqueued)
  Running     → Queued        (worker died, job reclaimed)
  Queued      → Cancelled     (CancelJob RPC)
  Running     → Cancelled     (CancelJob RPC — via CancellationToken)
  Invalid transitions return Err, never panic

SCHEDULER STATE (core concurrent data structures)
--------------------------------------------------
SchedulerState {
  job_queue:      Arc<Mutex<BinaryHeap<QueuedJob>>>,  // exclusive on dequeue
  running_jobs:   Arc<DashMap<JobId, RunningJob>>,    // hot read path
  completed_jobs: Arc<DashMap<JobId, CompletedJob>>,  // hot read path
  workers:        Arc<DashMap<WorkerId, WorkerInfo>>, // hot read path
  retry_queue:    Arc<Mutex<BTreeMap<Instant, JobId>>>, // sorted by retry_at
  total_submitted: Arc<AtomicU64>,
  total_completed: Arc<AtomicU64>,
  total_failed:    Arc<AtomicU64>,
}
Rule: DashMap for maps read concurrently by many tasks (GetJobStatus hot path)
Rule: Mutex<BinaryHeap> for queue (exclusive access needed on dequeue)
Rule: NEVER hold queue lock while doing I/O (deadlock risk)

RETRY POLICY
-------------
RetryPolicy enum:
  NoRetry,
  FixedDelay { delay_ms: u64, max_attempts: u32 },
  ExponentialBackoff { base_ms: u64, multiplier: f64,
                       max_attempts: u32, max_delay_ms: u64 }

fn next_delay(attempt: u32) -> Option<Duration>
  → Some(delay) = retry after this duration (with jitter ±25%)
  → None = no more retries, dead-letter this job

Jitter: multiply computed delay by rand(0.75..1.25)
WHY: Without jitter, all retrying jobs retry simultaneously → thundering herd

HEARTBEAT + FAILURE DETECTION
------------------------------
- Worker sends Heartbeat RPC every 5 seconds (bidirectional streaming)
- Scheduler records last_heartbeat_at: Instant per WorkerInfo
- Background task scans every 10 seconds:
    if now - last_heartbeat_at > 15 seconds → worker = Dead
    → move all worker's running_jobs back to Queued state
    → remove worker from active pool
- 15s threshold = 3x heartbeat interval (minimum safe ratio)
- WHY 3x: tolerates 2 consecutive dropped packets without false positive
- Fixed threshold limitation: cannot adapt to network jitter (phi accrual does)
- Be able to explain this tradeoff in interviews

AT-LEAST-ONCE DELIVERY
-----------------------
This scheduler provides at-least-once delivery. NOT exactly-once.
A job CAN run twice if: worker completes it but scheduler crashes before
recording the completion.
Mitigation: job executors MUST be idempotent (safe to run twice).
Document this explicitly in README. Be able to explain in interviews:
"Exactly-once is impossible across system boundaries (scheduler → worker →
external world). We provide at-least-once with idempotent executors as the
recommended pattern. This is the same guarantee SQS provides."

LEADER ELECTION (Phase 3)
--------------------------
Use etcd — do NOT implement custom consensus.
Mechanism:
  1. On startup: grant etcd lease with 10s TTL
  2. Try PUT scheduler/leader with own node_id, attached to lease
  3. If PUT succeeds → become leader (start dispatch loop, renew lease every 3s)
  4. If key exists → become standby (watch key for changes)
  5. On leader death: lease expires, key deleted, standby wins new PUT
  6. New leader: loads incomplete jobs from SQLite, starts dispatch loop
WHY etcd: leader election requires distributed consensus. etcd solves this
correctly. Do not reinvent it. "My scheduler's value is in scheduling logic,
not re-implementing Raft."

SQLITE PERSISTENCE
-------------------
- Enable WAL mode: PRAGMA journal_mode=WAL (concurrent reads during writes)
- Every state transition → UPDATE jobs SET state=... WHERE id=...
- On restart: SELECT * FROM jobs WHERE state IN ('Queued','Running','Retrying')
- Running jobs on restart → become Queued (worker may have crashed)
- Completed/dead-lettered retained for 7 days (configurable)
- Schema: jobs table with all Job fields + state_history as JSON column

KNOWN LIMITATIONS (document honestly in README)
------------------------------------------------
- At-least-once delivery (not exactly-once)
- Fan-out depth=1 only (parent-child, no full DAGs)
- Single etcd node is still a SPOF
- No horizontal SQLite scaling
- No cluster membership changes at runtime
- No linearizable reads (eventual consistency for job state)
- Fixed heartbeat threshold (not adaptive phi accrual)

IMPORTANT DESIGN DECISIONS AND WHY
------------------------------------
DashMap vs Mutex<HashMap>: DashMap shards internally → concurrent reads don't
  block each other. GetJobStatus is the hot read path (many concurrent clients).
  A global Mutex serializes all reads. Use DashMap.

UUID v7 vs v4: v7 is time-ordered → database indexes are efficient, ListJobs
  ordering is free. v4 is random → index fragmentation, expensive ordering.

Bidirectional streaming heartbeat vs repeated unary: One persistent gRPC stream
  per worker vs one RPC per heartbeat. At 100 workers × 5s interval = 1200
  RPCs/min with unary. One stream per worker = 0 RPC overhead for heartbeats.

SQLite WAL mode: Default journal mode blocks concurrent reads during writes.
  WAL mode enables concurrent reads. Critical for GetJobStatus under load.

Heartbeat threshold = 3× interval: Tolerates 2 dropped packets without false
  positive (false worker death). 2× is too tight. 3× is the safe minimum.

Token bucket over sliding window: Token bucket allows controlled bursts. Sliding
  window is stricter. Token bucket is standard for job dispatch rate limiting.
