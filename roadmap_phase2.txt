  Read BEFORE storing any timestamps in your system.

[MUST] Implement the dispatch loop as a dedicated tokio task
  This task runs forever. It is the brain of the scheduler.
  
  Loop:
    1. Lock job_queue
    2. Peek at highest-priority job
    3. Find an available worker that supports that job_type
    4. If found: dequeue the job, unlock the queue, send to worker
    5. If not found: unlock the queue, sleep 10ms, retry
  
  CRITICAL: Lock → peek → check worker → dequeue → UNLOCK → then send to worker
  NEVER hold the lock while sending to a worker channel (deadlock if channel full)
  
  On dispatch: log job_id, job_type, priority, worker_id, queue_depth, latency_us
  On failed dispatch (worker unavailable): return job to queue, log reason

── DESIGN ───────────────────────────────────────────────────────────────────────

[MUST] Design heartbeat + failure detection on paper BEFORE coding
  Heartbeat parameters:
    interval: 5 seconds (worker sends heartbeat every 5s)
    threshold: 15 seconds (3× interval — tolerates 2 missed packets)
    scan_interval: 10 seconds (how often scheduler checks for dead workers)

  Sequence:
    1. Worker opens bidirectional gRPC stream to scheduler
    2. Worker sends HeartbeatRequest { worker_id, current_jobs, capacity } every 5s
    3. Scheduler receives → updates workers[worker_id].last_heartbeat_at = now
    4. Background task runs every 10s:
         for each worker in workers:
           if now - worker.last_heartbeat_at > 15s:
             mark worker.state = Dead
             for each job in running_jobs where job.worker_id == dead_worker:
               move job back to Queued state
             remove worker from active pool
    5. Dead worker can re-register (gets same deterministic worker_id)

  QUESTION to answer before coding:
    What happens to a job the dead worker was executing?
    Answer: state transitions Running → Queued (reclaimed). The job will run again
    on another worker. This is at-least-once delivery. The worker may have
    actually completed it — we don't know. The executor must be idempotent.

  WHY bidirectional streaming (not repeated unary):
    One persistent gRPC stream per worker.
    At 100 workers × 5s interval = 1200 RPCs/min with unary RPCs.
    With streaming: 0 connection overhead, 1 stream per worker.

[MUST] Implement the failure detection background task
  tokio::spawn a task that runs every 10 seconds.
  
  fn scan_for_dead_workers(state: Arc<SchedulerState>) {
    let dead_workers: Vec<WorkerId> = state.workers
      .iter()
      .filter(|w| now - w.last_heartbeat_at > Duration::from_secs(15))
      .map(|w| w.worker_id.clone())
      .collect();
    
    for worker_id in dead_workers {
      state.workers.get_mut(&worker_id).unwrap().state = WorkerState::Dead;
      
      // Reclaim all jobs from this worker
      let reclaimed: Vec<JobId> = state.running_jobs
        .iter()
        .filter(|j| j.worker_id == worker_id)
        .map(|j| j.job_id.clone())
        .collect();
      
      for job_id in reclaimed {
        let job = state.running_jobs.remove(&job_id).unwrap();
        // Transition: Running → Queued
        state.job_queue.lock().push(QueuedJob::from(job));
      }
      
      log!(worker_id, jobs_reclaimed=reclaimed.len(), "worker declared dead");
    }
  }

  IMPORTANT: Do not hold workers lock while modifying running_jobs (deadlock).
  Collect dead workers first, release lock, then reclaim jobs.

── RISKS ────────────────────────────────────────────────────────────────────────
  [RED] Using unary Heartbeat RPCs instead of bidirectional streaming.
  At 100 workers × 5s interval = 1,200 RPCs/minute just for heartbeats.
  Use ONE persistent bidirectional stream per worker. Zero connection overhead.

  [RED] Testing with SIGTERM instead of SIGKILL. Graceful shutdown (SIGTERM) is

  [AMBER] Heartbeat task and dispatch loop deadlocking on workers DashMap.
  If both try to lock the same shard simultaneously, DashMap handles it.
  But if you have nested locks (workers → running_jobs → queue), you can deadlock.
  Always acquire locks in a consistent order.

── NOTES ────────────────────────────────────────────────────────────────────────
  Failure detection is the hardest part of this project. Not the queue, not the
  gRPC — the failure detection. A slow worker and a dead worker are
  indistinguishable from outside. Your 15-second threshold is a bet: if a worker
  is dead, you wait up to 15 seconds. If it's just slow, you may falsely declare

[MUST] Design retry flow and DLQ on paper BEFORE coding
  Extend the week 1 state machine:

  On job failure (worker reports error):
    retry_count += 1
    if retry_count < max_attempts:
      delay = retry_policy.next_delay(retry_count)  // with jitter
      set state = Retrying { retry_at: now + delay, attempts: retry_count }
      add to retry_queue (BTreeMap<Instant, JobId>, sorted by retry_at)
    else:
      set state = DeadLettered { reason: last_error }
      move to dlq DashMap

  Retry scheduler background task (runs every 1 second):
    for each job in retry_queue where retry_at <= now:
      remove from retry_queue
      set state = Queued
      push to job_queue (with original priority)

  IMPORTANT: Retrying jobs go to a SEPARATE sorted queue (not the main priority
  queue). The retry_queue is a BTreeMap<Instant, JobId> sorted by when to retry.
  DO NOT re-enqueue immediately — the delay must be respected.

    - No job retries MORE than max_attempts times (retry_count survives restart)
  
  If retry_count is lost on restart: a job gets extra retries beyond max_attempts.
  This is a bug. Verify retry_count in SQLite matches in-memory value for all jobs.

── RISKS ────────────────────────────────────────────────────────────────────────
  [RED] At-least-once: a job can run twice if the worker completes it but the
