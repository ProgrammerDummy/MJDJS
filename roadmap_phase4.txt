[MUST] Prepare and answer 15 deep technical questions OUT LOUD
  Time each answer: target 2–3 minutes. Record yourself on 3 of them and watch back.
  
  1. How does leader election work?
     Answer: etcd lease with 10s TTL. On startup, race to PUT scheduler/leader key
     with lease attached. Winner becomes leader, losers watch the key and retry
     on key deletion. Leader renews lease every 3 seconds.
  
  2. What happens to in-flight jobs when the leader dies?
     Answer: They stay in SQLite as state=Running. When the standby becomes leader,
     it loads all jobs where state=Running and transitions them back to Queued.
     The new leader then dispatches them to available workers. This is at-least-once
     — the worker may have completed the job before the crash, so it might run twice.
  
  3. Why at-least-once and not exactly-once?
     Answer: Exactly-once is impossible across system boundaries. The scheduler
     cannot atomically execute a job AND record its completion. If the scheduler
     crashes between those two events, the job ran but wasn't recorded. The only
     correct guarantee across boundaries is at-least-once. We mitigate with
     idempotent executors — jobs produce the same result if run twice.
  
  4. How do you choose the heartbeat threshold?
     Answer: 3× the heartbeat interval. At 5-second heartbeats, the threshold is 15
     seconds. This tolerates 2 consecutive dropped packets without declaring a live
     worker dead (false positive). Going to 2× is too tight — one jittered packet
     causes a false alarm. Going beyond 4× delays reassignment of real failures.
  
  5. What is priority starvation and how do you prevent it?
     Answer: A constant stream of high-priority jobs can prevent low-priority jobs
     from ever running. We prevent it with aging: a job's effective_priority is
     boosted by 1 every N seconds it waits. Eventually a low-priority job reaches
     a high enough effective_priority to run.
  
  6. How does tag-based routing work?
     Answer: Workers declare a map of tags on registration (e.g., gpu=true). Jobs
     declare a requirements map on submission. A job routes to a worker only if
     the job's requirements are a subset of the worker's tags. This is equivalent
     to Kubernetes node selectors — any engineer who has used Kubernetes will
     immediately understand it.
  
  7. How does the token bucket rate limiter work?
     Answer: A bucket has a capacity and a refill rate (tokens/sec). Before each
     dispatch, the scheduler tries to consume one token. If the bucket is empty,
     it waits until the next token arrives. Tokens refill continuously (not in
     batches) to prevent burst behavior. We use integer tokens to avoid float drift.
  
  8. What does the job state machine look like?
     Answer: States: Queued, Running, Succeeded, Failed, Retrying, DeadLettered.
     Transitions are implemented as fn transition(state, event) -> Result<state, error>.
     Invalid transitions (e.g., Succeeded → Running) return Err — never panic.
     [Draw the state machine on a whiteboard if available.]
  
  9. How do cron jobs survive failover without double-firing?
     Answer: Each cron job records last_fired_at in SQLite. The tick loop has an
     idempotency guard: before firing a cron job, it computes the current interval's
     start time and checks if last_fired_at >= interval_start. If so, the cron job
     already fired this interval (perhaps the old leader fired it), and we skip it.
  
  10. What is your job submission throughput?
      Answer: [fill in from BENCHMARKS.md] On school hardware with SQLite WAL
      enabled, approximately X,000 submissions/sec RPC overhead. Without persistence
      (in-memory only) it's Y,000/sec — the delta is the WAL write cost of Zms/job.
  
  11. What is your failure detection latency p99?
      Answer: [fill in from BENCHMARKS.md] Across 20 SIGKILL tests on school
      hardware, mean detection is Xs, p99 is Xs. The variance is driven by the
      heartbeat scan interval (10 seconds) plus propagation delay.
  
  12. What would you do differently if starting over?
      Answer: I'd use an in-memory message broker (like Redis streams) for job
      dispatch instead of pure gRPC — it would simplify the scheduler state and
      provide built-in persistence semantics. I'd also implement phi accrual failure
      detection instead of the fixed threshold, which would reduce false positives
      under variable network conditions.
  
  13. How would you add exactly-once semantics?
      Answer: You would need the worker to atomically write the result AND delete
      the "processing" lease in a single transaction. This requires the worker to
      participate in the scheduler's persistence layer — the result write and the
      job completion acknowledgment must be atomic. Practical approach: give each
      job a unique idempotency key, have workers write results to a shared database
      with an upsert (idempotency key + result), and have the scheduler check this
      database before declaring a job failed. This is how Stripe implements it.
  
  14. How would you scale to 1,000 workers?
      Answer: The current bottleneck is the dispatch loop — single-threaded, one
      dispatcher. To scale: shard the job queue by job_type into multiple queues,
      each with its own dispatcher. Each shard can then run independently. The
      worker heartbeat overhead (1,000 streams) is manageable with the current
      bidirectional streaming design. The SQLite bottleneck would require sharding
      by job_id hash across multiple SQLite files or switching to PostgreSQL with
      connection pooling.
