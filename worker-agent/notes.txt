What a job is here

Concretely, in your system: job_type (routing key — which executor runs it), payload (the input), priority, requirements (must match a worker's capabilities), retry_policy, metadata (opaque tags). The scheduler never inspects payload — it routes on job_type, matches on requirements, and hands payload to whatever executor the worker has registered.

payload: u64 is deliberately minimal. Your SleepJob interprets it as milliseconds. A real system would make it bytes — serialized JSON, protobuf, whatever the executor expects — because "which file, which URL, which arguments" doesn't fit in a number. That widening is a real change (proto plus both crates), and it's the main thing standing between this and running actual work.

The general shape: a job is a unit of deferred work with an identity and a lifecycle. The identity is what makes retry and status queries possible. The lifecycle is what your state machine encodes.

Why SQLite over Postgres

Three reasons, and they're worth being able to state cleanly:

No separate process. SQLite is a library that writes to a file. Postgres is a server you deploy, configure, monitor, and back up. For a scheduler whose whole value proposition is "one binary, run it," adding a database daemon doubles the operational surface.

Your access pattern doesn't need it. Postgres earns its complexity with concurrent writers across machines, complex joins, replication. Your scheduler is a single process writing its own state — one writer, simple key lookups. SQLite in WAL mode gives you concurrent reads alongside a single writer, which is exactly your shape.

Latency. SQLite is an in-process function call. Postgres is a network round trip. On a path that fires on every state transition, that difference compounds.

The honest counterargument for Phase 3: with two scheduler nodes, each has its own SQLite file. A newly-elected leader rebuilds from its file, which may lag the old leader's. Postgres would give both nodes one shared store. But that trades your SPOF for a database SPOF, and etcd is already handling the coordination problem. Worth knowing the tension exists.

What a distributed job scheduler is

Something has work that shouldn't happen inside a request. A user uploads a video; transcoding takes four minutes; the HTTP request can't wait. So you enqueue "transcode this" and return immediately. Something else picks it up and runs it.

The scheduler is that something else — plus the guarantees around it: the work isn't lost if a machine dies, it gets retried on failure, high-priority work goes first, and you can ask what happened to it.

"Distributed" because the work runs on machines other than the one that requested it, which is what makes failure detection and at-least-once delivery necessary at all.

Where you'll find them: Celery (Python), Sidekiq (Ruby), Temporal, AWS Batch, Airflow, Kubernetes Jobs. Every large system has one, usually several.

Typical workloads: media processing, ETL and report generation, email and notification sending, ML training and batch inference, data migrations, scheduled cleanup. The common thread is work that's too slow, too resource-hungry, or too failure-prone to run inline.
